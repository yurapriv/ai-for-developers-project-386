# Создание коммита

## Границы задачи

- Создавай коммит только по явному запросу пользователя. Просьба подготовить сообщение или добавить этот скилл не разрешает коммит.
- Соблюдай `AGENTS.md` и вложенные инструкции для затронутых файлов. Не изменяй код ради коммита без согласования.
- Не делай push, amend, rebase, reset, checkout файлов, очистку индекса или обход hooks без отдельного явного разрешения. Не меняй Git-конфигурацию и авторство.

## 1. Изучи изменения

Выполняй команды отдельно, из корня репозитория:

```sh
git status --short --branch
git diff --stat
git diff
git diff --cached --stat
git diff --cached
git log -5 --format=%s
```

- `git diff` не показывает untracked-файлы: прочитай новые файлы, которые планируется включить.
- Определи одну логическую цель коммита. Несвязанные изменения оставь нетронутыми; если границы неясны, уточни состав у пользователя.
- Уже staged-изменения не считай автоматически разрешёнными: проверь их принадлежность задаче. Если в индексе есть посторонние изменения, остановись и согласуй состав, не сбрасывая индекс.
- Если файл частично staged, не добавляй его целиком: сохрани границы подготовленных изменений и уточни неоднозначность.
- Проверь кандидатов на секреты, токены, приватные ключи, локальные env-файлы, дампы и ненужные артефакты. Секреты не включай в коммит и не цитируй в ответе; при обнаружении остановись и сообщи путь. `.gitignore` не защищает уже отслеживаемые файлы.
- При незавершённом merge/rebase или конфликтах остановись; разрешение конфликтов — отдельная задача. Если изменений нет, сообщи об этом, не создавая пустой коммит.

## 2. Проверь

- Найди команды проверок в инструкциях, manifest/task-runner конфигурации и CI. Запусти проверки, относящиеся к изменению, соблюдая установленный в проекте порядок.
- Не придумывай команды и не устанавливай новый toolchain ради коммита. Если проверки отсутствуют или недоступны, явно укажи это; не выдавай отсутствие запуска за успех.
- При ошибке проверки остановись и сообщи результат. Не обходи ошибку без явного согласования.

## 3. Подготовь индекс и сообщение

- Добавляй только проверенные пути через `git add -- "путь"`. Не используй `git add .`, `git add -A`, `git commit -a` или принудительное добавление ignored-файлов.
- После проверок и staging заново просмотри **полный** `git diff --cached` и `git diff --cached --stat`, затем выполни `git diff --cached --check`. Убедись, что тесты или форматтеры не добавили неожиданные изменения.
- Сообщение описывает фактический staged diff, а не планы и не все изменения рабочей директории.
- Соблюдай явно заданные правила проекта. При их отсутствии используй Conventional Commits:

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footers]
```

- Типы: `feat` — новая возможность, `fix` — исправление; для остальных изменений выбирай подходящий `docs`, `test`, `refactor`, `perf`, `build`, `ci` или `chore`. Scope необязателен, не выдумывай его.
- По умолчанию пиши заголовок по-английски, в повелительном наклонении, без точки; стремись уложиться в 72 символа. Это рекомендация, не требование спецификации.
- Body добавляй, только если нужно объяснить причину или важное ограничение. Для несовместимых изменений используй `!` или footer `BREAKING CHANGE: ...` и опиши последствия. Не выдумывай номера задач, результаты тестов и trailers авторства.
- Перед коммитом кратко сообщи пользователю состав и выбранный заголовок. Если запрос и границы ясны, повторное подтверждение не требуется.

## 4. Создай и проверь результат

- Выполни `git commit -m "<заголовок>"`; при необходимости передай body отдельным `-m`. Передавай текст безопасно для текущей оболочки, без интерполяции содержимого сообщения.
- При отказе hooks остановись и сообщи причину. Не используй `--no-verify`; после исправления повтори проверки и обзор индекса. Если коммит уже создан, не исправляй его через amend без запроса.
- После успешного коммита выполни:

```sh
git log -1 --format=fuller --stat
git status --short
```

- В ответе укажи короткий hash, заголовок, выполненные проверки и существенные пропуски. Сообщи, если остались незакоммиченные изменения. Не утверждай, что CI прошёл, без подтверждения.
