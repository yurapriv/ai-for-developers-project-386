# Создание коммита

## Границы задачи

- Запрос на коммит, включая вызов `@commit`, запускает подготовку плана, но не заменяет его одобрение. Создавай коммиты только после явного апрува конкретного плана пользователем.
- Просьба подготовить сообщения или изменить этот скилл не разрешает создание коммитов.
- До апрува не изменяй индекс или рабочие файлы: только изучи изменения, предложи план и дождись ответа.
- Соблюдай `AGENTS.md` и вложенные инструкции для затронутых файлов. Не изменяй код ради коммита без согласования.
- Не делай push, amend, rebase, reset, checkout файлов, очистку индекса или обход hooks без отдельного явного разрешения. Не меняй Git-конфигурацию и авторство.

## 1. Изучи изменения

Выполняй команды отдельно, из корня репозитория:

```sh
git status --short --branch
git diff --stat
git diff
git diff --cached --stat
git diff --cached
git log -5 --format=%s
```

- Рассмотри все staged, unstaged и untracked-изменения, включая сделанные пользователем. Если пользователь явно ограничил область, анализируй только её и перечисли оставленное вне плана.
- `git diff` не показывает untracked-файлы: получи полный список через `git ls-files --others --exclude-standard` и прочитай их перед включением в план. Ignored-файлы автоматически не включай.
- Разбей изменения по самостоятельным целям, а не по числу файлов или каталогам. Реализацию, её тесты и необходимую документацию обычно держи вместе; независимые исправления и рефакторинг разделяй. Если цель одна, предложи один коммит, не дроби искусственно.
- Для каждого изменения укажи группу либо причину исключения. Не оставляй посторонние изменения без внимания: вынеси их в отдельную группу или явно отметь неопределённость для согласования.
- Зафиксируй исходные границы индекса, особенно для частично staged-файлов. Staged-статус не означает одобрение. Если индекс содержит несколько будущих групп, включи в план необходимость его переразбиения и запроси отдельное явное разрешение на изменение существующего staging; не очищай индекс автоматически.
- Один файл может содержать несколько логических изменений: опиши группы на уровне фрагментов diff. Если разделение небезопасно или зависит от других групп, предложи объединение либо порядок с объяснением.
- Проверь кандидатов на секреты, токены, приватные ключи, локальные env-файлы, дампы и ненужные артефакты. Секреты не включай в коммит и не цитируй в ответе; при обнаружении остановись и сообщи путь. `.gitignore` не защищает уже отслеживаемые файлы.
- При незавершённом merge/rebase или конфликтах остановись; разрешение конфликтов — отдельная задача. Если изменений нет, сообщи об этом, не создавая пустой коммит.

## 2. Предложи план и получи апрув

- Покажи нумерованный план в порядке выполнения. Для каждого коммита укажи:
  - логическую цель и краткое описание изменений;
  - точные пути и, если файл разделяется, относящиеся к группе фрагменты;
  - предлагаемый заголовок и body/footers, если они нужны;
  - планируемые проверки, зависимости от других коммитов и известные ограничения.
- Отдельно перечисли исключённые изменения с причинами. Все сообщения составляй по фактическим diff соответствующих групп, а не по планам разработки.
- Используй `question`, чтобы предложить одобрить весь план, выбрать отдельные группы или изменить разбиение. Если инструмент недоступен, задай вопрос в ответе и остановись. Не выполняй staging или commit в ожидании ответа.
- Явный апрув всего плана разрешает выполнить всю предложенную последовательность без подтверждения каждого коммита. При выборе отдельных групп выполняй только их; не включай зависимости молча.
- Изменение состава, разбиения или сообщения после апрува требует повторного согласования затронутой части. Перед выполнением повторно проверь status и diff: новые изменения не входят в прежнее одобрение.

### Формат сообщений

- Соблюдай явно заданные правила проекта. При их отсутствии используй Conventional Commits:

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footers]
```

- Типы: `feat` — новая возможность, `fix` — исправление; для остальных изменений выбирай подходящий `docs`, `test`, `refactor`, `perf`, `build`, `ci` или `chore`. Scope необязателен, не выдумывай его.
- По умолчанию пиши заголовок по-английски, в повелительном наклонении, без точки; стремись уложиться в 72 символа. Это рекомендация, не требование спецификации.
- Body добавляй, только если нужно объяснить причину или важное ограничение. Для несовместимых изменений используй `!` или footer `BREAKING CHANGE: ...` и опиши последствия. Не выдумывай номера задач, результаты тестов и trailers авторства.

## 3. Проверь одобренные изменения

- Найди команды проверок в инструкциях, manifest/task-runner конфигурации и CI. Запусти проверки, относящиеся к одобренным группам, соблюдая установленный в проекте порядок.
- Не придумывай команды и не устанавливай новый toolchain ради коммита. Если проверки отсутствуют или недоступны, явно укажи это; не выдавай отсутствие запуска за успех.
- Учитывай, что проверки рабочей директории видят и незакоммиченные изменения других групп. Не утверждай, что каждый промежуточный коммит проверен изолированно, если проверялось только общее состояние.
- При ошибке проверки останови последовательность и сообщи результат. Не обходи ошибку без явного согласования. Изменения от форматтеров и исправлений тоже требуют обзора и, если меняют план, нового апрува.

## 4. Выполни одобренный план

Для каждой одобренной группы по порядку:

- Подготовь в индексе только её изменения. Добавляй целые файлы через `git add -- "путь"` лишь когда все их изменения относятся к группе. Для отдельных фрагментов используй проверенный patch и `git apply --cached`; если безопасное разделение невозможно, остановись и согласуй новый план.
- Не используй `git add .`, `git add -A`, `git commit -a` или принудительное добавление ignored-файлов. Не сбрасывай существующий staging без отдельного разрешения.
- Просмотри **полный** `git diff --cached` и `git diff --cached --stat`, затем выполни `git diff --cached --check`. При ошибке остановись. Индекс должен точно соответствовать одобренной группе, без изменений следующих или исключённых групп.
- Убедись, что одобренное сообщение соответствует staged diff. При расхождении остановись и запроси новый апрув, не исправляй сообщение или состав молча.
- Выполни `git commit -m "<заголовок>"`; при необходимости передай body отдельным `-m`. Передавай текст безопасно для текущей оболочки, без интерполяции содержимого сообщения.
- При отказе hooks остановись и сообщи причину. Не используй `--no-verify`; после исправления повтори проверки и обзор индекса. Если коммит уже создан, не исправляй его через amend без запроса.
- После успешного коммита выполни:

```sh
git log -1 --format=fuller --stat
git status --short
```

- После каждого коммита проверь оставшиеся изменения перед переходом к следующей группе. При сбое останови последовательность, сохрани уже созданные коммиты и сообщи, какая часть плана осталась невыполненной; не откатывай историю автоматически.
- В итоговом ответе перечисли короткие hash и заголовки всех созданных коммитов, выполненные проверки и существенные пропуски. Сообщи, какие изменения остались незакоммиченными. Не утверждай, что CI прошёл, без подтверждения.
