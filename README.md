## Сценарий владельца и гостя

В приложении один заранее заданный владелец календаря. Владелец и гость работают без регистрации и авторизации.

1. **Владелец создаёт тип встречи.** Указывает название, описание и длительность — например, «Знакомство», «Обсудим задачу», 30 минут.
2. **Гость открывает каталог типов встреч.** Смотрит описание и длительность, выбирает «Знакомство».
3. **Гость выбирает день.** Открывает календарь в пределах скользящего окна записи на 14 календарных дней и видит свободное время для выбранного типа встречи.
4. **Гость выбирает слот.** Например, 10:00–10:30. Длительность слота соответствует длительности типа встречи; весь интервал должен быть доступен владельцу.
5. **Гость подтверждает запись.** Заполняет форму записи и отправляет её. Состав полей будет определён в спецификации.
6. **Приложение создаёт запись.** Если интервал всё ещё свободен, гость видит подтверждение с типом встречи, датой и временем. Если время уже заняли, в том числе пока гость заполнял форму, пересекающаяся запись не создаётся.
7. **Владелец видит результат.** Открывает общий список предстоящих встреч всех типов и видит новую запись на «Знакомство» с выбранной датой и временем.

Время 10:00–10:30 приведено только для примера: рабочие часы и часовой пояс пока не выбраны.

### Обязательные правила и границы

- Занятость общая для всех типов встреч: запись на 10:00–10:30 запрещает любую другую встречу, пересекающую этот интервал, даже частично. Встреча с началом ровно в 10:30 допустима, если остальное время свободно.
- Запрет пересечений действует и при одновременных запросах: из двух запросов на пересекающиеся интервалы успешно создаётся не более одной записи.
- Окно записи сдвигается с течением времени. Начало с сегодняшнего или завтрашнего дня, рабочие часы, часовой пояс и шаг доступных стартов будут зафиксированы в спецификации.
- Регистрация, личные кабинеты, внешние календари и уведомления Cal.com в проект не входят.
- Допускается хранение в памяти процесса. Если выберем его, перезапуск будет сбрасывать записи; это ограничение нужно будет указать в README. Сохранение данных после перезапуска не является отдельным условием приёмки.

### Требования к будущей реализации

- Приложение должно собираться в Docker-образ и запускаться в контейнере.
- API описывается TypeSpec-контрактом; из него генерируется OpenAPI-спецификация, а из OpenAPI — клиентский SDK для фронтенда. До выбора инструментов необходимо проверить наличие генератора для языка фронтенда.
- Серверные типы и маршруты генерируются, если выбранный фреймворк это поддерживает. Иначе бекенд реализуется по контракту и проверяется тестами.

### Источники сценария

Сценарий учебного приложения основан на описании задания Хекслета. В [Cal.com](https://cal.com) просмотрен публичный гостевой путь до формы подтверждения; реальная бронь не отправлялась. Создание типа встречи и список владельца требуют входа, поэтому эти части изучены по официальной справке: [создание типа встречи](https://cal.com/help/event-types/create-first-event) и [просмотр записей](https://cal.com/help/bookings/manage-a-booking). Дополнительные возможности Cal.com не становятся требованиями нашего приложения.
