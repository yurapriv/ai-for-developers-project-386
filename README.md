Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Сценарий владельца и гостя

В приложении один заранее заданный владелец календаря. Владелец и гость работают без регистрации и авторизации.

1. **Владелец создаёт тип встречи.** Указывает название, описание и длительность — например, «Знакомство», «Обсудим задачу», 30 минут.
2. **Гость открывает каталог типов встреч.** Смотрит описание и длительность, выбирает «Знакомство».
3. **Гость выбирает день.** Открывает календарь в пределах скользящего окна записи на 14 календарных дней и видит свободное время для выбранного типа встречи.
4. **Гость выбирает слот.** Например, 10:00–10:30. Длительность слота соответствует длительности типа встречи; весь интервал должен быть доступен владельцу.
5. **Гость подтверждает запись.** Заполняет имя и email и отправляет форму записи.
6. **Приложение создаёт запись.** Если интервал всё ещё свободен, гость видит подтверждение с типом встречи, датой и временем. Если время уже заняли, в том числе пока гость заполнял форму, пересекающаяся запись не создаётся.
7. **Владелец видит результат.** Открывает общий список предстоящих встреч всех типов и видит новую запись на «Знакомство» с выбранной датой и временем.

Время 10:00–10:30 приведено только для примера. Расписание — ежедневно 09:00–18:00, Europe/Moscow.

### Обязательные правила и границы

- Занятость общая для всех типов встреч: запись на 10:00–10:30 запрещает любую другую встречу, пересекающую этот интервал, даже частично. Встреча с началом ровно в 10:30 допустима, если остальное время свободно.
- Запрет пересечений действует и при одновременных запросах: из двух запросов на пересекающиеся интервалы успешно создаётся не более одной записи.
- Окно записи сдвигается с течением времени: сегодня и следующие 13 московских календарных дней; шаг доступных стартов — 30 минут.
- Регистрация, личные кабинеты, внешние календари и уведомления Cal.com в проект не входят.
- Допускается хранение в памяти процесса: перезапуск сервера сбрасывает каталог встреч. Сохранение данных после перезапуска не требуется.

### Требования к будущей реализации

- Приложение собирается в Docker-образ и запускается в контейнере.
- API описывается TypeSpec-контрактом; из него генерируется OpenAPI-спецификация, а из OpenAPI — клиентский SDK для фронтенда. До выбора инструментов необходимо проверить наличие генератора для языка фронтенда.
- Серверные типы и маршруты генерируются, если выбранный фреймворк это поддерживает. Иначе бекенд реализуется по контракту и проверяется тестами.

### Источники сценария

Сценарий учебного приложения основан на описании задания Хекслета. В [Cal.com](https://cal.com) просмотрен публичный гостевой путь до формы подтверждения; реальная бронь не отправлялась. Создание типа встречи и список владельца требуют входа, поэтому эти части изучены по официальной справке: [создание типа встречи](https://cal.com/help/event-types/create-first-event) и [просмотр записей](https://cal.com/help/bookings/manage-a-booking). Дополнительные возможности Cal.com не становятся требованиями нашего приложения.

## Стек

- Бекенд: Go, стандартный `net/http`, generated strict server от oapi-codegen.
- Фронтенд: TypeScript, React, Vite, React Router 7; страницы: главная, каталог типов встреч `/booking`, создание типа встречи `/admin`, страница ошибки.
- API: `api/main.tsp` → `api/generated/openapi.yaml` → Go API и TypeScript Fetch SDK (Hey API).
- Проверки: Go testing, golangci-lint, Oxlint, Oxfmt, tsc, Playwright; hk и commitlint для Git hooks.
- Окружение и задачи: mise; dev-процессы — mise daemons / pitchfork. Версии закреплены в конфигурации и manifests проекта.

Реализованы гостевой каталог `/booking`, создание типа встречи в `/admin` и контейнерный запуск. Выбор слота и запись ещё не реализованы; вход не предусмотрен, внешняя публикация — отдельная задача.

## Запуск в контейнере

Нужен работающий Docker. Из корня репозитория:

```bash
docker build -t calendar-booking .
docker run --rm -p 127.0.0.1:8080:8080 calendar-booking
```

Откройте http://127.0.0.1:8080/admin, создайте тип встречи и проверьте каталог на http://127.0.0.1:8080/booking. API доступен на том же адресе под `/api/`, например `/api/meeting-types` и `/api/health`; dev-серверы не нужны. Остановите контейнер через Ctrl+C. В образ включены данные часовых поясов Go, включая Europe/Moscow; системный часовой пояс не задаёт правила расписания.

Это учебный запуск, не настройка внешнего production-хостинга. Авторизации нет: раздел владельца публичен. Используйте только тестовые персональные данные. Каталог изначально пуст и сбрасывается при перезапуске контейнера; постоянное хранение не настроено.

Контейнерная smoke-проверка собирает образ, запускает отдельный контейнер на свободном порту и проверяет API, прямые URL и сценарий в Chromium. Помимо Docker, нужны зависимости проекта и браузер Playwright (`mise run setup`, `mise run setup:e2e`):

```bash
mise exec -- node scripts/container-smoke.mjs
```

## Установка

Для локальной разработки нужны Git и **mise 2026.10.25**. Go, Node.js и остальные CLI устанавливает mise. Docker и WSL для этого не требуются; для контейнерного запуска нужен Docker.

Установите mise по [официальной инструкции](https://mise.jdx.dev/installing-mise.html). Для Windows есть проверяющий SHA-256 helper `scripts/install-mise.ps1`: он устанавливает mise в `~/.local/bin` без изменения постоянного PATH или профиля. Если политика PowerShell запрещает scripts, используйте ручную установку ZIP из официальной инструкции; менять ExecutionPolicy не нужно.

Если mise установлен в пользовательский каталог, на Windows достаточно добавить его в PATH **текущего** терминала:

```powershell
$env:PATH = "$HOME\.local\bin;$env:PATH"
mise --version
```

После клонирования:

```bash
git clone https://github.com/yurapriv/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install --locked
mise run setup
mise run setup:e2e
mise run setup:hooks
```

Перед `mise trust` прочитайте `mise.toml`, `hk.pkl` и `scripts/`: задачи исполняют локальный код. Установка hooks явная и действует только на этот клон. Локальный launcher сохраняет абсолютный путь к mise, поэтому Git/GUI не требуют изменения постоянного PATH. После переноса mise повторите `mise run setup:hooks`.

`setup` использует `npm ci` и Go modules; не устанавливает hooks и браузеры, не меняет глобальные настройки и не запускает серверы. `setup:e2e` отдельно устанавливает Chromium для Playwright; в CI на Linux он же ставит системные зависимости (`--with-deps`). Секретов и `.env` для каркаса не требуется.

## Использование

В двух терминалах:

```bash
mise run dev:backend
mise run dev:frontend
```

Откройте http://127.0.0.1:5173. Главная страница «Календаря встреч» ведёт в гостевой раздел `/booking` и «Админку» `/admin`; неизвестные адреса показывают страницу ошибки. Раздел `/booking` загружает каталог типов встреч, `/admin` — создаёт новые типы; обе страницы обращаются к Go API через прокси Vite `/meeting-types`. Остальные страницы этапа главной страницы статические и не обращаются к API — работающий Go-сервер для них не нужен. Go API по-прежнему отвечает на http://127.0.0.1:8080; Vite сохраняет прокси `/meeting-types` и `/health`. Бекенд принимает `LISTEN_ADDR` (по умолчанию `127.0.0.1:8080`); `127.0.0.1:0` позволяет ОС выбрать свободный порт.

Фоновый запуск, состояние, логи и остановка:

```bash
mise daemons start backend frontend
mise daemons ls
mise daemons logs backend frontend
mise daemons stop backend frontend
```

Foreground- и daemon-серверы используют одинаковые порты: сначала остановите один вариант перед запуском другого. Автозапуск при входе в ОС/переходе в каталог не настраивается; daemons — экспериментальная возможность mise.

### Проверки и сборка

```bash
mise run check
```

Это же вызывает отдельный GitHub Actions workflow `quality` на каждый push: generation drift → форматирование → Go module integrity → lint → typecheck → сборка → Go test → браузерные тесты Playwright → проверка конфигурации hooks и новых сообщений коммитов. Старые шаблонные коммиты до принятого правила не переписываются. При падении Playwright отчёты `playwright-report/` и `test-results/` сохраняются артефактом с коротким сроком хранения.

Отдельные команды: `mise run lint`, `mise run typecheck`, `mise run build`, `mise run test`, `mise run setup:e2e`. `test` сам собирает фронтенд и запускает Go- и Playwright-тесты: предварительный `mise run build` не нужен. `check` использует свою же сборку без повторной сборки фронта. Результаты сборки — `dist/server` (`server.exe` в Windows) и `dist/frontend/`. `npm run format` — отдельная изменяющая файлы команда; `check` ничего не исправляет и не добавляет в индекс.

Smoke-тест запускает настоящий Go-бинарник на назначенном ОС порту, проверяет HTTP-ответ по OpenAPI и завершает свой процесс. Браузерные сценарии этапа главной страницы и этапа каталога типов встреч (навигация, история, мобильная геометрия, клавиатура, создание типа) покрыты Playwright с одним движком Chromium; Vitest не подключён. Сгенерированный SDK используется страницами каталога и формы, проверка в браузере остаётся частью сценариев.

### Изменение контракта

Правьте `api/main.tsp`, затем запускайте:

```bash
mise run generate
mise run check
```

Generated OpenAPI, Go и SDK сохраняются в Git и вручную не редактируются. `generate` заменяет только принадлежащие генераторам каталоги `api/generated/`, `internal/api/`, `frontend/src/api/generated/`. Проверка актуальности генерирует во временное дерево и сравнивает весь состав файлов, включая новые и удалённые.

### Git hooks

- pre-commit: быстрые проверки staged-файлов, без исправлений и автоматического staging;
- commit-msg: Conventional Commits, например `feat: add meeting types`;
- pre-push: полный `mise run check`.

После нового клонирования установите hooks через `mise run setup:hooks`; CI работает независимо от их установки. Автоматических релизов пока нет.
