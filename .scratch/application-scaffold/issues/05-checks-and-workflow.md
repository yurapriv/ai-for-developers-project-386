## Question

Каков минимальный набор команд и проверок для выбранного стека, который одинаково работает локально и на каждый push в Linux GitHub Actions?

Согласовать:

- Установку, запуск бекенда и фронтенда, сборку, генерацию API и SDK, линтер, typecheck и тесты; единую точку входа всех проверок.
- Дымовой тест настоящего запуска Go-приложения и успешного HTTP-ответа по emitted OpenAPI. Рассмотреть go test как runner этого теста вместо дублирующего Vitest запуска; отдельно решить, нужны ли TS/UI-тесты уже на этапе каркаса и как проверяется браузерный вызов через SDK.
- Git-хуки, Conventional Commits, управление dev-процессами и отклонения от mise / hk / pitchfork, если они нужны для Windows.
- Фиксацию версий Go/Node и TypeSpec/Go codegen/TS SDK; npm lockfile и Go module/checksum semantics, правила generated-файлов и проверку их актуальности.
- Отдельный workflow без изменений hexlet-check.yml; какие результаты реально можно подтвердить локально и что проверяется только после push.
- Критерий готовности каркаса и обновления AGENTS.md после инициализации агента.

Ответ — согласованный план реализации и приёмки, а не сама реализация.

## Answer

Пользователь подтвердил все пять предложений: общую проверку, хранение generated-артефактов в Git, hk с commitlint, mise daemons с pitchfork и один Ubuntu workflow. Планирование каркаса завершено; ниже — согласованный интерфейс и приёмка для последующей реализации, не существующие команды.

### Команды и единая проверка

Будущий публичный интерфейс задач:

| Команда | Назначение |
| --- | --- |
| `mise run setup` | Установка зависимостей проекта по зафиксированным manifests; без глобальных настроек и неявной установки hooks |
| `mise run setup:hooks` | Явная установка локальных hk hooks для этого клона |
| `mise run dev:backend` | Go-сервер в текущем терминале |
| `mise run dev:frontend` | Vite в текущем терминале |
| `mise run generate` | TypeSpec → OpenAPI → Go server/types и TypeScript Fetch SDK |
| `mise run lint` | Go и TypeScript lint, без исправлений |
| `mise run typecheck` | Строгая проверка TypeScript, включая используемый generated SDK |
| `mise run build` | Сборка Go-бинарника и production-фронтенда |
| `mise run test` | Go test runner, включая настоящий process/HTTP smoke |
| `mise run check` | Все принятые проверки одной командой, одинаково локально и в CI |

`check` включает проверку форматирования, актуальности generated-файлов, зависимостей Go, lint, typecheck, сборку и тест. Ошибки передаются наружу; обязательные шаги не пропускаются при отсутствии тестов/файлов. Проверки не исправляют код и не меняют staging. Для последовательностей использовать переносимый task graph или явный process runner, а не полагаться на синтаксис одной оболочки.

### Инструменты проверок

- Go: стандартный gofmt, go vet, go build, go test и golangci-lint. Падение format gate определяется наличием отличий: один вывод gofmt -l не гарантирует ошибочный exit code.
- TypeScript: Oxlint, Oxfmt и отдельный tsc. Один компилятор; ESLint/Prettier/Biome параллельно не устанавливаются. Oxfmt pre-1.0 принят как исследованный кандидат с точным pin и проверкой фактической работы.
- Vitest и Playwright на этапе каркаса не устанавливаются. Go smoke не дублируется TS-runner-ом; отдельные UI-тесты добавятся вместе с функциональностью.
- Commitlint проверяет Conventional Commits. Правило также записывается в обновлённый AGENTS.md; release-please не подключается.
- govulncheck, architecture/coverage gates и дополнительные инструменты подборки не включаются автоматически: пользователь согласовал минимальный набор, а не всю подборку.

Документально исследованные исходные pins для реализации: mise 2026.10.25, golangci-lint 2.15.0, Oxlint 1.90.0, Oxfmt 0.75.0, hk 2.11.0, pitchfork 2.33.0, commitlint CLI/config-conventional 21.2.4. Кандидат frontend compiler — TypeScript 7.0.2 с React 19.3.1, Vite 8.3.5 и plugin-react 6.2.1. Поддержка полного разрешённого дерева и generated TS подтверждается установкой и проверками; несовместимость не обходится force/legacy-peer-deps и не скрывается вторым компилятором. Существенная замена инструмента требует согласования.

### Контракт и generated-артефакты

TypeSpec — единственный исходный контракт. Emitted OpenAPI, generated Go server/types и Fetch SDK коммитятся и вручную не редактируются. Состав и содержание generated-каталогов проверяются повторной генерацией, включая новые, удалённые и ещё не tracked файлы; одного git diff недостаточно.

Предпочтительный read-only check генерирует во временное собственное дерево и сравнивает ожидаемые артефакты, не исправляя рабочие файлы. `generate` — отдельная намеренно изменяющая артефакты команда для разработчика. Нельзя удалять пользовательские untracked-файлы или требовать чистоты всего worktree ради drift-проверки.

Go server использует generated strict interface/route registration, request validation по общему контракту и контрактный тест ответа; compile-time types не объявляются полной runtime validation. Подробная семантика и подходящие библиотеки — в [исследовании Go](06-go-backend.md).

### Дымовой тест и браузерная приёмка

Один Go smoke строит/запускает настоящий бинарник приложения отдельным процессом и выполняет реальный GET /health. Проверяет HTTP 200, JSON Content-Type и соответствие ответа emitted OpenAPI, а не дублированной ручной схеме.

Порт назначается ОС; фактический адрес получает тест. Есть конечные startup/request/test deadlines, диагностика раннего завершения и cleanup с ожиданием завершения именно своего процесса при успехе и ошибке. Не запускать долгоживущий go run wrapper и не завершать чужие node/go-процессы. Приёмочный test запускается без использования старого test cache.

При внедрении показать, что неверный ответ/ошибка запуска действительно приводят к падению gate; затем восстановить правильное состояние и повторить проверку. Это техническая проверка самого gate, не функциональность бронирования.

Отдельно вручную в браузере проверить frontend: видны состояния загрузки, успешного ответа и ошибки, запрос проходит через generated SDK и настроенный proxy либо согласованный CORS. Browser smoke не выдаётся за автоматизированный E2E-тест.

### Hooks и Conventional Commits

hk устанавливается явно, локально для клона, без изменения глобального Git config:

- pre-commit: быстрые format/lint checks для применимых staged-файлов;
- commit-msg: commitlint по сообщению создаваемого коммита;
- pre-push: полный `mise run check`.

Hooks не исправляют и не добавляют файлы в индекс. Обязательна проверка частичного staging: пользовательские unstaged-изменения сохраняются и не попадают в коммит. Существующие hooks сначала исследуются и не перезаписываются молча. Глобальные настройки и обход hooks не входят в план.

CI повторяет gates независимо от установки/обхода локальных hooks. Для проверки сообщений использовать безопасно переданный диапазон новых коммитов с обработкой новой ветки/недоступного before; исторические сообщения до внедрения правила не переписывать и не объявлять причиной переделки истории. Нельзя интерполировать текст сообщений в shell script.

### Dev-процессы

Frontend и backend описываются в mise daemons. В project config включается experimental, версия pitchfork закрепляется. Предусмотреть явные start/status/logs/stop и проверяемую readiness; обычные foreground dev-задачи остаются доступными.

Автоматический запуск при входе в Windows или смене каталога не настраивается. На PowerShell auto lifecycle не обещается. Проверить повторный start и остановку без оставшихся процессов/занятых портов. CI smoke самостоятельно управляет своим процессом и не зависит от запущенных dev-daemons.

### Зависимости, версии и CI

- В mise фиксируются точные Go/Node/tool версии и env; для Go GOTOOLCHAIN=local предотвращает скрытую смену компилятора. Bootstrap-версия самого mise фиксируется отдельно.
- В проекте один npm manifest/lockfile; CI использует npm ci. Go module versions задаёт go.mod/MVS, go.sum содержит checksums и не называется lockfile выбора версий. Проверять tidy drift и module integrity, не писать checksums вручную.
- Генератор oapi-codegen запускается с точной версией, без глобального latest; source/outputs обоих генераторов согласованы. Нужные платформенные pins/lock metadata включают Windows и Linux.
- Отдельный собственный workflow на push, один Ubuntu job (исходный вариант ubuntu-24.04), с конечным timeout, минимальными permissions и проверенными полными SHA используемых actions. Установка из зафиксированных manifests и тот же `mise run check`; дополнительные CI-проверки истории вызывают те же commitlint-настройки, что hook.
- Отдельная Windows CI-задача откладывается; native Windows проверяется локально. Существующий hexlet-check.yml остаётся без изменений.
- Локальный зелёный check и зелёный Actions — разные свидетельства. CI можно подтвердить только после отдельно разрешённого push и просмотра результата; наличие YAML не является успешным CI run.

### Порядок реализации и критерий готовности

1. Подготовить user-local mise и согласованные инструменты; проверить версии и Windows shell/architecture. Изменение постоянного PATH/profile или установка WSL/Docker не делаются неявно.
2. Создать минимальные TypeSpec-контракт, Go-сервер на generated interfaces и React/Vite health-страницу с SDK по официальным getting started, без бизнес-функций.
3. Добавить перечисленные проверки, hooks, daemons и отдельный CI; закрепить manifests и артефакты.
4. Выполнить clean setup, generation/drift, check и браузерную проверку на Windows; проверить отрицательные случаи gates, partial staging и cleanup. Установку hooks выполнить явно, после просмотра конфигурации.
5. После появления рабочего каркаса выполнить инициализацию агента (/init) и сократить AGENTS.md до реальных команд, структуры и неочевидных правил; сохранить ограничения Hexlet и указатели docs/agents, добавить Conventional Commits. Устаревшие сведения о пустом репозитории заменить фактами. Обновить README с рабочими setup/run/check командами, сохранив сценарий владельца/гостя.
6. Отдельно согласовать коммиты и push. После разрешённого push подтвердить зелёный собственный workflow; до этого явно указывать, что CI не проверен.

Готовность каркаса — реальные локальные запуск обоих слоёв и браузерный SDK-вызов, зелёный общий check, проверенная установка hooks/управление daemons, актуальные короткие инструкции и подтверждённый собственный CI. План не расширяется на Docker, деплой, релизы или бронирование.

На момент закрытия билета создан только план. Установки, application-код, генерация, lint/typecheck/build/tests, hooks/daemons и GitHub Actions ещё не выполнялись; staging, коммиты и push не делались.
