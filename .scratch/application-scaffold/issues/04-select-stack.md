# Выбрать стек и локальное окружение каркаса

Type: grilling
Status: resolved
Blocked by: 01, 02, 03, 06

Исследования: [цепочка API и варианты стека](01-api-toolchain.md), [окружение Windows и Linux CI](02-windows-environment.md), [dev-guardrails и проверки](03-dev-guardrails.md).

## Question

Какой стек и способ подготовки окружения выбираем по результатам исследований, учитывая TypeSpec → OpenAPI → SDK, нативную Windows как приоритет, допустимость WSL и Linux CI?

С пользователем согласовать бекенд, фронтенд, UI-библиотеку либо её отложенное подключение, Node.js, менеджер пакетов, генератор SDK и путь серверной реализации контракта. Явно назвать требования установки и ограничения. Не выбирать инструменты только по памяти модели.

Ответ должен отделять выбранные инструменты от альтернатив и давать проверяемые критерии для реализации каркаса.

## Context pointers

- [Проверить цепочку TypeSpec → OpenAPI → TypeScript SDK и варианты стека](01-api-toolchain.md): основная SDK-цепочка подтверждена документально, серверная генерация не является автоматически полной.
- [Проверить воспроизводимое окружение Windows и Linux CI](02-windows-environment.md): native Windows возможен; WSL не обязателен по исследованной документации.
- [Сверить тесты, линтеры, хуки и CI с dev-guardrails](03-dev-guardrails.md): текущая подборка предлагает Oxc и отдельную проверку типов, не установку всех инструментов сразу.

При согласовании версии TypeScript учесть расхождение рекомендаций исследований: API-отчёт сохраняет TS 5.9.3 ради запасного SDK-инструмента, отчёт проверок рассматривает TS 7. Выбрать один компилятор по фактически принятой цепочке; не добавлять запасной генератор и не понижать версию только ради неиспользуемой альтернативы.

## Comments

Пользователь предпочёл попробовать Go для бекенда; он iOS-разработчик и пока мало знаком с веб-стеком. Node.js-бекенд не выбран. Нужна проверка Go getting started и серверной генерации из того же OpenAPI, прежде чем рекомендовать Go-framework/toolchain. См. [Проверить Go-бекенд и генерацию сервера из OpenAPI](06-go-backend.md).

Подтверждены: простой сервер вместо сложной экспериментальной связки; серверная генерация допустима и должна быть рассмотрена при наличии подходящего инструмента; UI-библиотека на этапе каркаса откладывается; mise принят для версий и задач. Приоритет native Windows сохраняется. TypeScript-фронтенд и Node/npm как инструменты сборки пока предложены отдельно от Go-бекенда, подтверждение ожидается.

Следующим ответом пользователь подтвердил TypeScript + React + Vite для фронтенда и Go для бекенда. Node.js/npm остаются инструментами фронтенда, TypeSpec и SDK, а не runtime бекенда. Сгенерированный SDK связывает эти слои через HTTP-контракт. Конкретные Go-инструменты и серверный генератор ожидают исследования; окончательные pins и API-генератор ещё не согласованы.

Исследование Go завершено: [Проверить Go-бекенд и генерацию сервера из OpenAPI](06-go-backend.md). Теперь возможно предложить net/http / ServeMux и oapi-codegen со strict server без отдельного framework и без отказа от серверной генерации. Прежняя рекомендация ручных маршрутов для Fastify не переносится автоматически на Go.

## Answer

Пользователь подтвердил итоговую связку и предложил двигаться дальше. Выбран стек:

| Часть | Решение |
| --- | --- |
| Бекенд | Go 1.27.3, стандартные net/http и ServeMux; без Fastify, Hono, chi и Gin |
| Генератор Go API | oapi-codegen v2.8.2: модели, strict-интерфейс обработчиков, std-http adapters и регистрация маршрутов; вручную — реализация интерфейса и запуск сервера |
| Фронтенд | TypeScript + React + Vite; Mantine, shadcn/ui и другая UI-библиотека на этапе каркаса не подключаются |
| Контракт | TypeSpec как единственный источник; emitted OpenAPI 3.0.0 YAML — общий вход Go-генератора и генератора SDK |
| Генератор SDK | Hey API с TypeScript Fetch SDK, без отдельного Go-клиента для браузера |
| Node toolchain | Node.js 24.22.2 LTS и bundled npm 11.19.1 только для фронтенда, контракта и SDK, не runtime Go-бекенда |
| Окружение | mise; основной локальный путь — native Windows / PowerShell, CI — Linux; WSL пока не устанавливается |

Документально проверенные исходные pins контрактных инструментов — TypeSpec compiler/http/openapi/openapi3 1.17.0 и Hey API 0.99.0. Версия mise, точные React/Vite/TypeScript pins и остальные проверочные инструменты фиксируются при подготовке единой конфигурации по исследованной совместимости, без latest и конкурирующих TS-компиляторов.

### Почему так

- Go соответствует предпочтению пользователя; стандартный HTTP-стек не требует изучать дополнительный framework.
- Наличие подходящего oapi-codegen позволяет выполнить требование серверной генерации без экспериментальных Fastify/Hono-интеграций. Прежнее условное согласие на ручные маршруты не используется для отказа от доступного Go codegen.
- Фронтенду не требуется Go/WebAssembly: он обращается к бекенду по HTTP через сгенерированный SDK.
- Оба генератора получают один emitted контракт; generated-файлы вручную не редактируются.

### Критерии реализации и ограничения

1. Единственная техническая операция на этапе каркаса — GET /health с JSON-ответом по TypeSpec; бизнес-API не добавляется.
2. Go health-обработчик реализует generated strict interface и подключается generated-регистрацией маршрутов, а не параллельным ручным route вне контракта.
3. Фронтенд получает ответ Go-бекенда через generated Fetch SDK; браузерный доступ и настройки proxy/CORS проверяются фактически.
4. Generated-типы не выдаются за runtime validation. Проверка запросов и контрактного ответа, runner дымового теста, hooks и единая команда согласуются в следующем билете.
5. Точные версии, dependency manifests и полученные lock/checksum-файлы сохраняются в проекте. Совместимость полного дерева и generated-кода подтверждается реальной установкой, генерацией, сборкой и тестами, а не только таблицами metadata.
6. Выбор стека не разрешает автоматически менять PATH, профили shell, глобальную Git-конфигурацию, устанавливать WSL/Docker, создавать коммиты или делать push. Установка и реализация выполняются после согласования следующего плана; ограничения Hexlet сохраняются.

Альтернативы и первоисточники остаются в закрытых исследовательских билетах, перечисленных выше. На момент решения установки, генерация, сборка и тесты не выполнялись.
