# Сверить тесты, линтеры, хуки и CI с dev-guardrails

Type: research
Status: resolved

## Question

Какие проверки и инструменты рекомендует первоисточник dev-guardrails для небольшого TypeScript-проекта, git-хуков и GitHub Actions, и что из этого оправдано уже на этапе каркаса?

- Найти первоисточник подборки dev-guardrails из задания Хекслета; в репозитории URL отсутствует. Подтвердить происхождение. Если источник нельзя однозначно установить, явно отметить неопределённость, не приписывать рекомендации случайному одноимённому проекту.
- По первоисточникам проверить рекомендации и актуальные варианты линтера / форматтера, typecheck, тестового раннера, хуков и CI. TypeScript / React / Vite пока кандидаты.
- Предложить минимальную общую проверку с одним дымовым тестом: настоящий запуск процесса приложения и успешный HTTP-ответ, завершение процессов, timeout и отсутствие конфликтов портов. Отличать такую проверку от in-process injection.
- Проверить совместимость вариантов с Windows и Linux CI, фиксацию версий и воспроизводимую установку зависимостей.
- Рассмотреть фиксацию Conventional Commits в AGENTS.md и соразмерную автоматизацию без release-please и лишнего набора инструментов.

Результат — рекомендации со ссылками, различение обязательного и опционального, а не установка инструментов или написание кода.

## Answer

Подборка установлена с высокой уверенностью: `mokevnin/dev-guardrails` перенаправляет на `mokevnin/dev-quality-gates`; ссылка на исходный адрес есть в официальном шаблоне Hexlet `hexlet-boilerplates/ai-metarepo`. Связь с конкретной редакцией календарного упражнения публично не подтверждена. Проверенный snapshot подборки: `829848c77853988cee6683b0d3bfe4904181be95`.

Актуальные Recommendations / tools.json предлагают Oxlint + Oxfmt и отдельную строгую проверку типов; старая исследовательская заметка с ESLint не является текущей рекомендацией. Подборка не требует ставить весь набор инструментов. Oxfmt пока pre-1.0; ESLint с typescript-eslint требует отдельной проверки совместимости с выбранной версией TypeScript. Окончательный lint/format набор ещё не выбран.

Vitest предложен как соразмерный TS/Vite runner, а не как обязательный выбор подборки. Дымовой тест должен запускать настоящий собранный сервер дочерним процессом и проверять HTTP-ответ, иметь ограниченные ожидания и cleanup; in-process injection этого не заменяет. Браузерный E2E runner для одного такого теста необязателен.

Рекомендованы общий read-only `check`, locked dependency install, отдельный Ubuntu workflow на каждый push, явная установка hooks и правило Conventional Commits. Commitlint и дополнительные quality gates остаются отдельными опциями, не автоматически обязательными зависимостями.

Подробности, опубликованные версии и первоисточники: [Scaffold: тесты, линтеры, хуки и CI относительно dev-guardrails](file:///C:/Users/prive/AppData/Local/Temp/opencode/scaffold-guardrails-research/docs/research/scaffold-guardrails.md).
