# Главная страница «Календаря встреч»: инструкция исполнителю

Статус: план согласован, реализация не начата. Документ описывает только этот этап, а не весь сервис записи.

## Точка входа и границы

1. Прочитай корневой `AGENTS.md`, `docs/agents/domain.md`, `GLOSSARY.md` и `docs/adr/0001-client-side-navigation.md`.
2. Выполни `git status --short`: сохрани чужие изменения; если они пересекаются с задачей, согласуй дальнейшие действия.
3. Работай из корня репозитория. Перед командами mise в PowerShell добавь `$HOME\.local\bin` в PATH текущего процесса, как описано в README.

Результат этапа — статическая главная страница, две заглушки, обработка неизвестного адреса и браузерные тесты в существующей системе проверок. Реализуй только описанное ниже.

Сохрани API, `/health`, Go-тесты и генерацию без изменений. Генерируемые каталоги принадлежат генераторам. `.github/workflows/hexlet-check.yml` и имя репозитория защищены требованиями Hexlet. Бронирование, каталог типов встреч, формы, управление расписанием, вход, Docker и публикация находятся вне этапа. Установка Git hooks требует отдельного запроса пользователя.

## Ветка и завершение через pull request

- Исключение для подготовки: `GLOSSARY.md`, этот план и согласованный ADR можно закоммитить непосредственно в основную ветку `main` после отдельного явного одобрения пользователем конкретного плана коммита. PR для этих подготовительных документов не нужен. Их коммит не разрешает начинать реализацию или делать push без соответствующего запроса.
- До изменений кода создай отдельную ветку задачи от актуальной основной ветки репозитория; непосредственно в основной ветке фичу не разрабатывай. Подготовительные документы сохраняются в истории основной ветки и доступны исполнителю; не создавай для них отдельный PR.
- Реализация включает Conventional Commits, push рабочей ветки и создание pull request в GitHub со всеми относящимися к нему изменениями. Это часть согласованного результата задачи; при отсутствии доступа сообщи блокер, а не объявляй задачу завершённой.
- Перед коммитами используй skill `commit` и согласуй предлагаемый план коммитов. Для описания PR используй skill `pr`. Перед обращениями к GitHub Issues прочитай `docs/agents/issue-tracker.md`; дополнительные tickets для этой задачи не создавай без запроса.
- Перед push проверь итоговый diff и выполни `mise run check`. После push проверь результаты GitHub Actions для последнего коммита рабочей ветки. Если запуски ещё идут или недоступны, явно укажи это в PR и итоговом отчёте.
- Каждый PR должен быть самостоятельно проверяемым и проходить существующие проверки. Код, его тесты и необходимые изменения запуска/CI поставляются вместе, а не отдельными сломанными промежуточными PR.
- Согласован один PR на всю реализацию: страницы, маршруты, стили, тесты, их запуск, CI и обновление README. Подготовительные документы уже входят в основную ветку отдельным коммитом и не требуют собственного PR. Иное разбиение согласуй с пользователем до работы; stacked PR не создавай.
- Оставляй PR открытым для ревью. Merge, включение auto-merge, force push и изменение настроек репозитория не входят в задачу.
- В финальном отчёте дай ссылки на все PR фичи, укажи охват каждого, результаты локальных проверок и CI. Если работа не дошла до открытого PR, сообщи, что осталось сделать.

## Контракт интерфейса

| Маршрут | Единственный `h1` | Остальное содержимое |
| --- | --- | --- |
| `/` | Календарь встреч | «Выберите удобное время и запишитесь онлайн»; ссылки «Записаться» → `/booking` и «Админка» → `/admin` |
| `/booking` | Запись на встречу | «Этот раздел пока в разработке»; ссылка «На главную» → `/` |
| `/admin` | Админка | «Этот раздел пока в разработке»; ссылка «На главную» → `/` |
| Любой неизвестный путь | Страница не найдена | Ссылка «На главную» → `/`; исходный URL сохраняется |

- На всех страницах язык русский, заголовок вкладки — «Календарь встреч». В `frontend/index.html` установи `lang="ru"`, этот title и описание из главной страницы в meta description.
- «Записаться» — визуально основное действие, «Админка» — вторичное. Переходы реализуются ссылками React Router, а не кнопками с ручной сменой `window.location`.
- Простая адаптивная вёрстка: системный шрифт, ограниченная ширина контента, комфортные отступы, светлый фон, контрастный текст. Иллюстрации, UI-библиотеки и отдельный дизайн-проект не нужны.
- Каждая страница имеет `main`. Ссылки доступны с клавиатуры, фокус видим. При ширине 375 px нет горизонтальной прокрутки, действия не перекрываются.
- Прямое открытие, обновление и история браузера работают для всех маршрутов. Неизвестный путь — клиентская страница ошибки; HTTP 404 от Vite не является условием этого этапа.
- Удали технический экран и его запросы к `/health`, а не скрывай их стилями. Страницы этого этапа не требуют API.

## Контракт запуска тестов

- Добавь задачу `mise run setup:e2e`: запускай локальный CLI установленного `@playwright/test` через Node, устанавливая только Chromium. На Linux при `CI=true` устанавливай также системные зависимости через `--with-deps`. Задача выполняется явно после `mise run setup`; обычные тесты не устанавливают браузеры.
- Реализуй общую функцию запуска тестов в `scripts/tasks.mjs`, чтобы `test` и `check` использовали один набор Go- и браузерных проверок. Следуй существующему способу запуска локальных CLI, не полагайся на глобальные npm-пакеты или Unix-shell.
- `mise run test` самостоятельно собирает фронтенд и запускает Go-тесты и Playwright: предварительный `mise run build` не требуется. Полный `check` использует свою уже выполненную сборку без повторной сборки фронтенда. Остальные существующие проверки сохраняются.
- Playwright `webServer` запускает `node node_modules/vite/bin/vite.js preview --config frontend/vite.config.ts --host 127.0.0.1 --port 4173 --strictPort` из корня. `baseURL` и адрес ожидания готовности — `http://127.0.0.1:4173`.
- Playwright управляет готовностью, временем ожидания и завершением своего сервера. `reuseExistingServer: false`: занятый порт вызывает понятную ошибку, а не тестирование чужого процесса. Не останавливай чужие серверы.
- Для этого небольшого набора используй один worker, без retries. Основной проект — Chromium с desktop viewport; мобильный сценарий меняет viewport на 375 × 812 без второго движка и дополнительных устройств.
- Настрой trace и скриншот при падении. Добавь `/test-results/` и `/playwright-report/` в `.gitignore`. При отсутствии Chromium команда должна завершаться ошибкой с инструкцией установки, а не пропускать тесты.
- Расширь существующий lint на `playwright.config.ts` и `tests/e2e/`; typecheck также проверяет оба пути. Сохрани текущие проверки форматирования.

## Браузерные сценарии приёмки

Тесты изолированы; каждый начинает навигацию явно. Используй `getByRole` с точными доступными именами, web-first assertions Playwright и проверки URL. Для ожидания UI используй assertions, а не фиксированные задержки. Не заменяй навигацию моками и не используй CSS-классы как селекторы содержимого.

1. **Главная:** открыть `/`; проверить title, `main`, единственный заголовок «Календарь встреч», описание и обе ссылки с правильными href.
2. **Запись:** с главной нажать «Записаться»; проверить `/booking`, заголовок, сообщение; нажать «На главную» и проверить главную.
3. **Админка:** аналогично проверить `/admin`, его содержимое и возврат.
4. **Прямые ссылки и обновление:** открыть каждый из `/`, `/booking`, `/admin` напрямую, затем выполнить reload; проверить URL и соответствующий заголовок до и после обновления.
5. **История:** `/` → клик «Записаться» → browser back → `/` → browser forward → `/booking`; на каждом шаге проверить страницу.
6. **Неизвестный адрес:** открыть `/unknown-page`; проверить сохранение URL, заголовок ошибки и переход по «На главную».
7. **Независимость от API:** до открытия главной перехватить запросы к `/health` и прерывать их; проверить главную и переход на запись. Дополнительно проверить, что приложение вообще не запросило `/health`.
8. **Мобильный экран:** при 375 × 812 проверить видимость и доступность обоих действий и отсутствие горизонтального переполнения на всех четырёх видах страниц. Это проверка геометрии и навигации, не сравнение со скриншотом-эталоном.
9. **Клавиатура:** на главной добраться до «Записаться» клавишей Tab, проверить фокус, активировать Enter и проверить страницу записи. Аналогично проверить достижимость вторичной ссылки. Видимость focus-стиля дополнительно проверить вручную.

## Порядок реализации и контрольные точки

Выполняй шаги последовательно. После каждого сообщай изменённые файлы, выполненные команды и их результат. При ошибке исправляй причину; проверки не отключай и ожидаемые значения под ошибочное поведение не меняй. Если блокер находится вне согласованного объёма, сообщи его и остановись.

### 1. Страницы и навигация

Добавь router, четыре страницы и метаданные. Замени технический экран, API оставь неизменным. Проверь `mise run typecheck` и `mise run build`.

Готово, когда маршруты, ссылки, прямое открытие, обновление и история работают в Vite dev и Preview, включая неизвестный путь. Проверяй через существующие команды или явно запущенный Preview; заверши только свои тестовые процессы.

### 2. Оформление и доступность

Приведи стили к контракту интерфейса. Вручную проверь desktop, 375 px, клавиатуру и видимый фокус.

Готово, когда оба действия различимы, все ссылки доступны и страницы не переполняют мобильный viewport.

### 3. Playwright и локальные команды

Добавь конфигурацию, все девять сценариев, установку Chromium и интеграцию test/check/lint/typecheck. Выполни `mise run setup:e2e`, затем `mise run test` и `mise run lint` с `mise run typecheck`.

Готово, когда команды проходят на Windows без заранее собранного фронтенда и без работающих dev-серверов. Playwright не требует Go API; существующий Go smoke-тест по-прежнему сам запускает свой сервер.

### 4. GitHub Actions

В `quality.yml` между setup и check добавь установку Chromium через новую задачу. Сохрани существующие этапы и значения переменных проверки коммитов. При падении сохраняй существующие `playwright-report/` и `test-results/` через upload-artifact с ограниченным сроком хранения; отсутствие файлов не должно маскировать исходную ошибку. Для новой action выбери проверенный полный commit SHA официального релиза, как принято в workflow.

Готово локально, когда workflow валиден и `mise run check` проходит. Зелёный CI считается подтверждённым только после push рабочей ветки и чтения результата конкретного запуска. Если push заблокирован или CI ещё не завершён, явно укажи «CI не проверен», не объявляй его зелёным.

### 5. Документация и итоговая проверка

В README замени отображаемое название на «Календарь встреч», обнови описание текущей реализации, инструкции использования, проверок и установки Chromium. Удали устаревшие утверждения о health-экране и отсутствии браузерных тестов, сохрани описание будущего сценария сервиса. Название не распространяется на переименование GitHub-репозитория, URL, технических идентификаторов и исходных учебных материалов.

`GLOSSARY.md` содержит только термины; ADR — причины архитектурного выбора; этот план — задачи и критерии. Сверь их с реализацией, сохрани согласованный смысл.

Выполни форматирование изменённых файлов и полный `mise run check`. Предпочитай форматировать только свои изменения, поскольку общее `npm run format` изменяет файлы. Проверь итоговый diff на неожиданные изменения, особенно API, generated-файлы и защищённый workflow.

Готово, когда вся локальная проверка проходит, документация соответствует реализации, PR открыт для ревью, а итоговый отчёт содержит ссылки, результаты и реальные ограничения.
